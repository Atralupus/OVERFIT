# 패턴을 고르는 망 — 봇 함대 · 데이터 공장 · 학습 · 게임 안의 고르기 · 검증

**상태:** 설계 (2026-09-28) · 우산 이슈 #102
**잇는 설계:** `2026-09-24-보스전-재설계-design.md` 의 §4.4 「망이 들어오면」 · §6.2(겨냥 표) · §7(계측). 그 문서와 어긋나는 곳은

## 0. 무엇을 만드나

2단계의 고르기 자리(`stages.json` 의 `picker`)에 망을 넣는다. 망이 하는 일은 하나다.

> **이 플레이어에게 이 패턴을 내면, 맞을 확률이 얼마인가?**

무엇을 낼지는 망이 아니라 **규칙**이 정한다(§6.2 — 좁힌 명부). 망이 이상한 값을 내도 게임이 안 깨지게 나눈 것이다(README 「망이 답하는 질문」).
학습 데이터는 세상에 없으므로 성향이 다른 봇을 대량으로 돌려 직접 만든다 — 그래서 작업은 데이터부터 쌓아 올리는 순서다.

```
봇 함대 ──▶ 데이터 공장 ──▶ 학습 ──▶ 가중치 ─────────────────▶ 게임 안의 고르기
(규칙 층)    (.NET 콘솔)     (Python)  (overfit/data/network.json)  (규칙 층)
```

### 성공의 기준

- 성향을 올리면 짝지은 계측 축이 그쪽으로 움직인다 — 계측이 성향을 되찾지 못하면 망도 못 배운다(§3.4).
- 같은 함대 시드면 같은 학습 데이터가 나온다 — 스레드 수와 무관하게 바이트까지(§4.5).
- 학습 데이터 **원본에** 겨냥 표가 보인다 — 대시에 기대는 봇이 잡기에 더 맞는다 등(§4.6 — 2번 PR 이 재서 2026-09-24 §6.2 의 GIF 표에서 바꿨다).
- 떼어 둔 봇에서 망이 패턴의 기저율보다 잘 맞히고, "30% 라고 한 것이 30% 맞는다"(보정 · §5.5).
- 같은 봇들에게 망 보스와 무작위 보스를 붙이면 **기대던 수단이 막히고**(의존 봉인), **매 시도에 넘을 수 있는 패턴이 하나 남는다**(숨통 · §7).
- 파이썬이 따로 계산한 로짓과 C# 순전파의 로짓이 **비트까지** 같다(§8).
- 사람의 플레이에서 봇과 사람이 얼마나 다른지(sim-to-real)를 재는 도구가 선다 — 결과는 사람의 기록이 쌓이면 붙인다(§7.3).

### 대화로 정한 것 (2026-09-28)

| 물음 | 정한 것 |
|---|---|
| 망이 무엇을 읽나 | **손으로 정한 축**(A). 회피 기록 원본을 순서대로 읽는 모델(B)은 이 망이 끝나고 사람 데이터로 검증까지 한 뒤 여유가 있으면 따로 — 고르기 등록표 구조상 나중에 붙여도 A 를 안 연다 |
| 가드 축 | **11번째 축 `guard_rate`** = `GuardSamples / Samples`. 의존도 축과 셈법이 다르다(사용률)는 것을 주석에 적는다(§3.2) |
| 점수로 한 시도를 어떻게 채우나 | **좁힌 명부** — 겨냥 1~2개 + 숨통 1개, 그 안에서 무작위. 도드라진 습관이 없거나 근거가 얇으면 다섯 전부(§6.2) |
| 사람에게 대조군 비율 | **반반에서 시작** — `balance.json` 한 줄(§6.3). 2026-09-28 에 무작위 30% 로 줄였다(#122) |
| 망이 패턴을 무엇으로 아나 | **2단계 명부의 칸** — 칸마다 출력 하나. 태그로는 `3연격` 과 `엇박 3연격` 이 같아 못 가른다(§5.2) |
| 같은 시드면 같은 결과 | **결정 경로에 사칙연산만** — 시그모이드(exp)를 결정에 안 쓴다(§8) |
| 학습 데이터를 어떻게 모으나 | **실제 흐름 그대로** — 1단계를 싸우고 2단계를 재시도하며 패턴이 설 때마다 한 건(§4) |

### 가정한 것 — 틀리면 여기를 고친다

- **디스크의 시도 기록은 망의 기억이 아니다.** 되살리기와 사람 데이터 수집용 로그다. 고르기가 읽는 것은 지금처럼 **이번 런의 메모리 기록**이고,
  처음부터 하면 비운다(새 런은 1단계에서 다시 잰다 — 2026-09-24 §4.4 그대로).
- 캐릭터는 1종이라 망의 입력에서 뺀다 — 상수는 아무것도 안 가르친다. 캐릭터가 늘면 칸을 더하고 다시 학습한다.
- 사람의 기록은 유저(와 테스터)가 직접 플레이한 것이고, 파일을 손으로 옮겨 온다 — 자동 업로드는 없다.
- 학습은 이 클라우드 환경이나 유저의 맥에서 돈다. 커밋하는 것은 결과인 `network.json` 이다 — 학습의 재현은 같은 기기 · 같은 버전에서만 약속한다.

## 3. 봇 함대 (1번 PR)

### 3.1 사람처럼 늦고 흔들린다

`BattleSim` 의 주석이 이미 못박아 두었다 — 봇에는 **반응 지연과 잡음을 반드시 넣어야 한다.** 안 그러면 망이 "초인이 어떻게 실패하는가" 를
배우고, 그건 사람에게 아무 의미가 없다.

- 봇은 판정이 언제 서는지 안다(`NextActiveIn` — 선딜을 읽는 사람의 눈이다). 그러나 **선딜이 시작하고 제 반응 지연이 지나야** 움직일 수 있다.
  선딜이 반응보다 짧으면 늦는다 — 사람이 빠른 공격에 맞는 방식 그대로다.
- 누르는 시각 = 판정이 서는 시각 + 제 타이밍 편향 + 잡음. 그 시각이 알아챈 시각보다 이르면 알아챈 시각에 누른다.
- 잡음은 **균등 난수 넷의 합**(Irwin–Hall)을 편차에 맞춰 늘인 것이다 — exp · log · sqrt 없이 사칙연산만(§8).
- 스태미나가 모자라면 안 누른다(`Fighter.Affords`) — 지금의 `BotPolicy` 와 같다. 스스로 탈진하는 성향은 두지 않는다(§13).
- **끝까지 칠 수 있는 칼만 넣는다 — 욕심이 그 선을 넘는다** (1번 PR 의 관문이 찾았다). 칼질은 경직까지 커밋이라 다음 패턴이 설 때 칼 안에 있으면
  못 피한다. 다음 위험까지 1타 + 2타가 안 들어가면 1타만, 1타도 안 들어가면 안 친다 — 칼질마다 욕심의 몫만큼은 재지 않고 친다(README 의 욕심 —
  "위험한데도 공격을 욕심내나"). 이 선이 없으면 수단의 성향이 축에 안 닿는다: 거의 모든 봇이 제 칼에 묶여 맞는다.
- 간격을 두는 사람은 판정을 기다리는 동안 제 간격까지 물러선다 — 간격 습관의 첫 수단은 자리다.

### 3.2 `guard_rate` — 11번째 축

- `PlayerAxes.GuardRate = GuardSamples / Samples`. 근거가 없으면 0(NaN 을 안 낸다 — 다른 축과 같다).
- **의존도 축과 셈법이 다르다.** 의존도(`jump_reliance` · `parry_reliance`)는 "그 수단이 가능했고 다른 수단도 가능했던" 판정을 분모로 삼는다 —
  가능했던 수단이 드문 패턴만 만난 사람을 "안 골랐다" 로 세지 않으려는 것이다. 가드는 잡기 하나를 빼면 **모든** 판정에서 가능해 그 분모가 거의
  전부이고, 그러니 가드의 사용률은 그 자체로 정직한 값이다 — 의존도 축이 피하려던 혼동(드문 가능성)이 가드에는 없다. 1단계에는 가드 못 받는
  판정이 없어 분모 `Samples` 가 곧 "가드할 수 있었던 판정" 이다.
- 왜 지금인가: 2단계의 `1타 잡기` 는 가드를 안 받는다(겨냥 표 · §4.6 — 처음에는 `점프 3연속` 이 가드를 노린다고 적었다). 망이 가드에
  기대는 사람을 알아보려면 입력에 가드가 있어야 한다.
  `GuardSamples` 의 주석이 "입력 모양은 망을 세우는 자리에서 한 번에 정한다" 고 미뤄 둔 그 자리가 여기다.
- **같이 고칠 주석** (CLAUDE.md §9 — 낡은 주석은 없느니만 못하다): `PlayerAxes` 머리말("10개 숫자" · "열이라는 것이 계약"), `GuardSamples` 의
  「왜 11번째 축이 아닌가」, `DodgeVerb.Guard` 의 「11번째 축을 만들지 않는다」, README 「입력」의 10축 표. 데모의 `[axes][I]` 줄에 `guard_rate=` 를 싣는다.
- 골든은 안 움직인다 — 골든은 관측 스트림을 해시하지 축을 해시하지 않는다.

### 3.3 성향

한 봇의 성향은 **(함대 시드, 봇 번호)** 로 `Det` 에서 뽑는다 — 봇 번호 하나로 그 봇이 되살아난다. 범위는 `tools/factory/fleet.json` 이다:
게임의 수치가 아니라 **실험의 조건**이라 `overfit/data/` 가 아니고, 공장의 매니페스트가 그 파일의 해시를 싣는다.

| 성향 | 뜻 | 처음 범위 | 움직여야 할 축 |
|---|---|---|---|
| 수단 선호 | 판정이 오면 대시 · 점프 · 패리 · 가드 중 무엇으로 받나(비중 넷) | 절반은 **습관형**(한 수단 0.6~0.9, 나머지 고르게) · 절반은 **혼합형**(고르게 뽑아 정규화) | 대시 비중 · `jump_reliance` · `parry_reliance` · `guard_rate` |
| 반응 지연 | 선딜이 시작하고 몇 초 뒤에 알아채나 | 0.15 ~ 0.35 초 | `dash_timing_bias` · `jump_timing_bias` (빠른 판정에서) |
| 흔들림 | 누르는 시각의 편차 | 0.02 ~ 0.10 초 | `dash_timing_var` |
| 타이밍 편향 | 일찍 누르나 늦게 누르나 | −0.08 ~ +0.04 초 | `dash_timing_bias` · `jump_timing_bias` |
| 리듬 의존 | 판정을 눈으로 안 보고 **3연격의 박자로** 누르는 비율 | 0 ~ 1 | 1단계 축으로는 안 보인다 — §3.4 |
| 대시 방향 | 대시가 보스 쪽(안)인 비율 | 0 ~ 1 | `dash_direction_bias` |
| 거리 | 쉬는 동안 사거리 밖에서 기다리는 간격 · 습관형 "간격" 은 멀리 서서 후딜에만 찌른다 | 0 ~ 150 px · 간격 습관형 250 ~ 500 (1번 PR 에서 좁혔다 — 간격 습관형이 아닌 봇까지 멀리 서면 거의 모든 봇이 후딜에만 친다) | `distance_bias` |
| 욕심 | 보스가 휘두르는 순간에도 칼을 넣나 | 0 ~ 1 | `greed` |
| 2연격 | 1타를 누를 때 2타를 이을 작정인가 | 0 ~ 1 | `greed` (2타는 1초를 서는 칼이다) |

- 습관형의 "습관" 은 다섯이고 고르게 뽑는다 — 대시 · 점프 · 패리 · 가드 · 간격. 수단 넷의 습관이 겨냥 표(§4.6)의 네 줄이고, 간격 습관형은
  원본에 도드라진 칸이 없다(대조가 된다 — 2번 PR 이 쟀다).
- **리듬 의존이 있어야 엇박이 배워진다.** 엇박 3연격은 3연격과 여는 동작이 같고 타마다 선딜만 0.15 초 늦다 — 칼을 보고 누르는 사람은 여전히
  받아친다(2026-09-24 §4.9). 봇이 전부 눈으로 누르면 엇박은 누구에게도 더 어렵지 않고, 망은 "패리 의존 → 엇박" 을 영영 못 배운다.
  리듬형 행동은 **3연격의 판정 시각표**로 잰다 — 3연격과 여는 동작이 같은 패턴(`엇박 3연격` · `1타 돌진` · `1타 잡기` 의 1타)에서 그 비율만큼
  시각표를 따른다. 그 시각표는 규칙 층이 `patterns.json` 의 3연격 타임라인에서 읽는다(봇에 숫자를 박지 않는다 — CLAUDE.md §3).
- 새 난수 스트림 셋 — 도메인 번호는 뒤에 더할 뿐이다(CLAUDE.md §4 · §8 의 표).

### 3.4 관문 — 계측이 성향을 되찾나

1번 PR 의 합격선이다. **계측이 성향을 못 되찾으면 망도 못 배우므로 여기서 멈춘다.**

- 규칙 테스트: 성향 하나만 낮음 · 높음으로 바꾸고 나머지는 고정한 채, 시드 여섯으로 1단계를 돌려 관측을 모아 짝지은 축이 **같은 방향으로**
  선 이상 움직이는지 본다(표의 오른쪽 칸 — 성향마다 한 테스트). 중간은 뺐다 — 여섯 판으로는 가운데의 순서가 잡음에 흔들린다.
- **수단의 비중은 솜씨를 고정하고 본다.** 관측의 수단은 결과를 만든 것이라(`DodgeEvent.Verb`) 늦은 대시는 "안 피함" 으로 실린다 — 가운데
  타이밍으로 재면 수단의 축이 선호가 아니라 솜씨를 잰다. 비중 · 리듬의 관문은 타이밍이 좋은 봇 위에서, 편향의 관문은 반응을 빠르게 두고 돈다.
  재 본 값은 1번 PR 의 계획(`docs/superpowers/plans/2026-09-28-봇-함대.md`)에 있다.
- 리듬 의존만 다르다 — 1단계에서는 3연격의 시각표가 곧 실제 판정이라 축이 안 움직인다. 2단계 `엇박 3연격` 을 대본(`script`)으로 고정해 패리
  습관형의 **맞는 비율**이 리듬 의존을 따라 오르는지, 같은 봇이 `3연격` 에서는 **안 변하는지**(대조) 본다.
- 테스트가 스위트를 몇 초 늘린다 — 전투 한 판이 순수 .NET 으로 수십 ms 다(재 봄: 1단계 한 판이 JIT 포함 230 ms).

### 4.3 라벨 — 그 사례에 맞았나

- 사례의 관측 = 그 사례가 선 틱부터 다음 사례가 서기 전까지 나온 관측 중 **그 패턴 id 인 것**.
- **맞았다(1)** = 그중 하나라도 결과가 `Hit` · `GuardBroken` · `Grabbed` 다 — 피해를 제대로 받았거나 붙들렸다.
  **안 맞았다(0)** = 전부 `Dodged` · `Parried` · `Guarded` · 빗나감이다. 막아 낸 가드(칩 피해)는 막은 것이다 — 가드로 버티던 사람이 점프 ×3 의
  셋째 착지에서 무너지면 그 붕괴가 1 이다.
- **끝나지 않은 사례는 버린다** — 판이 그 사례 도중에 끝났는데(보스가 쓰러짐 · `max_ticks`) 안 맞았으면 "끝까지 버텼나" 를 모른다. 맞아서 쓰러진
  사례는 1 로 남는다. 보스가 탈진해 끊긴 사례(패리 · 경직 게이지)는 끝난 것이다 — 파이터가 이긴 교환이라 0 이다.
- 피해의 크기(칩 하나와 세 대가 같은 1)는 싣지 않는다 — §11.

한 줄이라도 안 보이면 멈춘다 — 봇의 모형이 그 습관을 못 흉내 내거나, 패턴이 설계대로 겨냥하지 않는 것이다. 어느 쪽이든 망이 배울 것이 없다.

**처음 표는 이것이 아니었다 — 2번 PR 이 재서 바꿨다.** 처음에는 README 의 GIF 표(2026-09-24 §6.2 — 대시 → 잡기 · 가드 → 점프 ×3 ·

멈추고 따라가 보니 봇의 결함 둘과 설계의 어긋남 둘이었다:

- **봇의 결함**(고쳤다 · #108): 누름이 한 틱 늦었고(편향 0 이 늘 한 틱 늦은 사람) · 리듬형을 타마다 선딜 + 반응에 묶어 두었다. 고친 뒤 리듬형
  패리의 엇박은 기저율보다 높아졌지만(봇 10,000 대 · 0.729 · 기저율 0.676) 들어 올림이 +0.25 로 `lift_min`(0.405) 아래다 — 욕심 · 편향 ·
  리듬이 아닌 누름이 엇박의 몫을 흐린다. 망은 리듬이 강한 사람에게만 엇박을 고를 것이다.
- **가드 → 점프 ×3 은 순서의 효과다.** 가득 찬 스태미나는 착지 셋을 다 막는다(2026-09-24 §4.8 의 산수 — 21.6 × 3 = 64.8 < 100). GIF 의
  붕괴는 3연격을 막아 스태미나가 준 **바로 뒤에** 점프 ×3 이 올 때만 선다. 고르기는 시도마다 명부를 좁혀 무작위로 뽑으므로(§6.2) 그 순서를
  못 만든다 — 망이 배울 수 있는 겨냥이 아니다. 원본에서 가드형은 점프 ×3 에 오히려 강하다(0.608 · 기저율 0.802).
- **간격 → 돌진은 모르는 사람의 실수다.** GIF 의 사람은 1타 뒤의 후딜에 걸어 들어가다 달려오는 보스를 찌른다. 그러나 돌진은 1.30초까지 3연격과
  한 틱도 다르지 않고(2026-09-24 §4.6), 1단계를 넘은 사람은 3연격의 2타가 온다는 것을 안다. 판정이 남은 후딜을 치는 습관으로 봇에 넣어 보니

- 입력 19(§4.7) → 32 → 32 → **5** · 은닉층은 ReLU. 모수 약 1,900.
- **출력은 2단계 명부의 칸마다 로짓 하나다.** 한 번 돌리면 다섯 패턴의 점수가 다 나온다. 머리의 순서 = `stages.json` 2단계의 `patterns` 순서
  (뽑기 좌표와 같은 칸) — `network.json` 의 `heads` 가 id 로 싣고, 데이터 테스트와 불러오기가 대 본다.
- **패턴 태그를 입력으로 쓰지 않는다.** `3연격` 과 `엇박 3연격` 의 태그가 완전히 같고(엇박은 박자만 다르다), 잡기의 핵심(대시 · 가드 · 패리를 안 받는
  판정)은 태그가 아니라 판정 단계에 있다 — 태그로 읽으면 "패리 의존 → 엇박" 을 배울 수 없다. 태그는 패턴의 요약으로 남고 데이터 테스트가 계속 본다.
  패턴을 더하면 머리가 늘고 다시 학습한다 — 새 패턴은 어차피 새 데이터가 필요하다.

### 5.3 학습

- 손실: 칸을 가린 이진 교차 엔트로피 — 사례 하나는 **제 칸의 머리만** 가르친다.
- 표준화: 학습 몫의 평균 · 편차. 편차가 0 인 열은 1 로 둔다(그 열은 아무것도 안 가르친다).
- 나누기: **봇 번호로** 학습 80 · 검증 10 · 시험 10. 같은 봇의 사례가 양쪽에 새면 망이 봇을 외운 것을 일반화로 착각한다.
- Adam · 조기 종료(검증 손실 · 6 에폭 참는다) · 시드 고정 · BLAS 한 스레드 — 같은 기기 · 같은 원본이면 같은 가중치다(다시 학습해 `network.json` 의
  sha256 이 같음을 봤다). 출력 층의 편향은 기저율의 로짓에서 시작한다 — 학습은 사람을 보고 그 위로 얼마나 오르내리나만 배운다.

### 5.4 기준선

- **패턴의 기저율** — 사람을 전혀 안 보고 "잡기는 누구에게나 35%" 라고만 말하는 예측기. 망이 이것을 못 이기면 축에 정보가 없다는 뜻이다.
- 각 칸의 기저율은 `network.json` 의 `baseline` 에 **로짓으로** 싣는다(§6.2 의 들어 올림이 쓴다). 로그는 파이썬에서만 한 번 — C# 은 그 수를 읽기만 한다.

### 5.6 `overfit/data/network.json`

```json
{
  "_comment": "…",
  "version": 1,
  "features": ["dash_timing_bias", "…", "parry_choice_samples"],
  "mean": [0.0, "…"],
  "std": [1.0, "…"],
  "heads": ["3연격", "점프 3연속", "1타 돌진", "1타 잡기", "엇박 3연격"],
  "baseline": [-0.62, "…"],
  "layers": [ { "w": [[…]], "b": […] }, { "w": …, "b": … }, { "w": …, "b": … } ],
  "trained_on": { "commit": "…", "data_digest": "…", "fleet_seed": 0, "bots": 0 },
  "metrics": { "test": { "…": "…" } }
}
```

- `w` 는 행이 출력 · 열이 입력이다. 수는 파이썬 `repr` 로 쓴다 — 가장 짧은 왕복 표기라 C# 의 `double.Parse` 가 같은 double 을 얻는다.
- 게임은 이 파일을 **필수 데이터**로 읽는다 — 키가 빠지면 부팅이 빠진 키를 나열하고 멈춘다(CLAUDE.md §3). 모양이 안 맞으면(층의 크기 · `features` 가
  `PlayerFeatures` 와 다름 · `heads` 가 2단계 명부와 다름 · 편차 ≤ 0) `[E]` 다 — 규칙 위반이다.
- **`data_digest`** = `overfit/data/` 의 `bosses` · `fighters` · `hitboxes` · `patterns` · `stages` 다섯 JSON 을 이름 순으로, 파일마다
  `이름 \0 길이 \0 바이트` 로 이은 것의 sha256(소문자 16진) — `overfit/core/DataDigest.cs` 한 자리다(2번 PR). 이름과 길이를 끼우는 까닭: 바이트만
  이으면 한 파일의 끝을 다음 파일의 머리로 옮겨도 같은 해시다.
  지금의 해시와 다르면 망이 배운 게임이 지금의 게임이 아니다 — 부팅은 `[W]` 한 줄을, `check` 는 경고 한 줄을 남긴다(이상하지만 계속 간다 — 실패로
  두면 수치 하나를 고칠 때마다 몇 시간의 공장이 막는다). `balance.json` 은 안 넣는다 — 뷰 수치(`feel`)와 고르기 수치(`picker`)가 섞여 있어 거짓 경보가 난다.
  규칙 **코드**의 변화는 리플레이 골든이 잡는다 — 골든이 움직이는 PR 은 망을 다시 학습할지 PR 설명에 적는다.

### 5.7 골든 — 파이썬과 C# 이 비트까지 같다

- `ml/golden.py` 는 **표준 라이브러리만** 쓴다(넘파이 없음). `network.json` 을 읽어 고정 입력 스무 개의 로짓을 C# 과 **같은 연산 순서**로
  계산한다: 표준화 `(x - mean) / std`, 층마다 출력 `j` 에 대해 `acc = b[j]` 에서 시작해 입력 순서대로 `acc += w[j][i] * z[i]`, 마지막 층을 빼고 ReLU.
  넘파이의 `dot` 을 안 쓰는 이유: BLAS 가 더하는 순서를 바꾸고 FMA 를 쓸 수 있다.
- 결과는 `tests/Overfit.Rules.Tests/Battle/NetworkGolden.json` — 입력과 기대 로짓. C# 테스트는 `==` 로 견준다(허용 오차 없음).
- `tools/build.sh check` 가 `golden.py --verify` 를 돈다(넘파이가 없어도 돈다) — 파이썬 == 골든 파일 == C# 이 매 커밋 선다. 망이 아직 없는
  체크아웃은 경고로 넘긴다.
- 넘파이(행렬곱 — BLAS 의 덧셈 순서)의 로짓과 골든(입력 순서의 덧셈)은 끝자리만 다르다 — `export.py` 가 1e-9 안인지 본다(행렬을 뒤집어 쓴 것 같은
  실수를 잡는다 · 3번 PR 에서 잰 차이는 8.9e-16).
- ReLU 는 `acc if acc > 0 else 0.0` 이다 — −0 과 NaN 에서 파이썬의 `max` 와 C# 의 `Math.Max` 가 다른 값을 내서 둘 다 이 모양으로 쓴다.

### 6.1 `PlayerNet`

### 6.2 `NetworkPicker` — 좁힌 명부

고르기 등록표(`PatternPickers`)의 새 id `network`. **시도를 시작할 때 한 번** 세운다 — 판 도중에는 안 바뀐다(2026-09-24 §4.4).

1. 입력 = `PlayerFeatures.From(이번 런의 기록)`.
2. `samples < picker.min_samples` 면 **다섯 전부**(`reason=thin`).
3. 로짓 `ℓ` 를 얻고, 칸마다 **들어 올림** `lift = ℓ - baseline` — 평균의 사람보다 이 사람에게 얼마나 더 잘 먹히나(로그 오즈 비).
4. **겨냥** = `lift ≥ picker.lift_min` 인 칸, 들어 올림이 큰 순서(같으면 앞 칸)로 많아야 `picker.max_targeted` 개. 없으면 **다섯 전부**(`reason=no_habit`).
5. **숨통** = 겨냥이 아닌 칸 중 로짓이 가장 낮은 칸(같으면 앞 칸) — 이 사람이 가장 덜 맞을 패턴이다.
6. 좁힌 명부 = 겨냥 ∪ 숨통, 명부 순서로. `Pick(draw)` = 좁힌 명부의 `Det.RollInt(시드, PatternPick, 좁힌 수, k1: draw)` 번째 칸.
   다섯 전부일 때는 `Det.RollInt(시드, PatternPick, 5, k1: draw)` — `uniform` 과 **비트까지 같다.**

- 고르기는 여전히 상태 없는 조회다(`draw` 번호 → 칸) — 보스의 순서는 시도를 여는 순간 정해진다. 되살리기가 그래서 된다(§6.5).
- **왜 들어 올림인가 — 약점 저격이 아니다.** 로짓 자체가 높은 칸(이 사람이 제일 못 버티는 패턴)을 고르면 약점 저격이고, 고르게 약한 초보자일수록
  가혹해진다(README). 들어 올림은 "평균의 사람보다 **이 사람에게 유독** 먹히는 패턴" 이다 — 고르게 약한 사람은 어느 칸도 도드라지지 않아 다섯
  전부로 돈다. 2단계의 패턴은 판정이 저마다 어떤 수단을 막으므로(겨냥 표 · §4.6) 도드라진 칸은 곧 그 사람이 기대는 수단을 막는 패턴이다.
  이것이 실제로 그런지는 5번 PR 이 잰다(§7 — 고르게 약한 봇).
- 1단계는 계속 `uniform` 이다 — 무엇에 기대는지를 재는 자리다.

**4번 PR 이 미리 쟀다 — 아직 약점 저격이 아니라고 못 한다.** 원본(§4.8)의 시험 몫(봇 90,000 ~ 99,999 · 2단계 시도 21,770)의 입력에 이 규칙을
그대로 돌렸다. 공장은 2단계를 무작위로 돌므로 2단계 첫 시도 뒤의 입력은 망 갈래의 것과 다르다 — 정식 측정은 5번 PR 의 평가 모드다(§7.1).

| 무리 | 다섯 전부 (thin + no_habit) | 기대한 칸이 겨냥에 든 시도 |
|---|---|---|
| 고르게 약한 봇(§7.1 의 정의) | **38.9%** (12.7 + 26.2) | — |
| 혼합형 전부 | 42.6% | — |
| 대시 | 13.3% | 70.8% (잡기) |
| 가드 | 9.5% | 90.4% (잡기) |
| 패리 | 17.9% | 76.4% (점프 3연속) |
| 점프 | 18.7% | 79.9% (돌진) |
| 간격 | 38.2% | — |

§7.1 의 「약점 저격이 아니다」(80% 이상이 다섯 전부)에 못 미친다. 망이 쏠림을 읽기는 한다 — 혼합형도 수단 비중이 고를수록 덜 좁힌다(가장 큰
비중 < 0.35 → 다섯 전부 52.7% · 0.35 ~ 0.45 → 44.9% · 0.45 ~ 0.55 → 33.5% · ≥ 0.55 → 22.0%). 그런데 비중이 고른 봇도 칸마다의 들어 올림이 평균
0.65 쯤 벌어져(가장 큰 칸 − 가장 작은 칸) `lift_min` 0.405 를 넘는 칸이 흔하다 — 수단 말고도 욕심 · 간격 · 이어치기 같은 성향이 칸마다 다르게
먹히는지, 근거가 얇아 흔들리는지는 아직 가르지 않았다. 들어 올림을 **그 사람의 평균 들어 올림에** 견주는 규칙(도드라짐 = lift − 다섯 칸의 평균 lift
≥ `lift_min`)도 재 봤다 — 고르게 약한 봇의 다섯 전부가 60.3% 로 오르지만 선에 못 미치고, 대시 → 잡기의 겨냥이 40.6% 로 떨어진다.

**규칙과 문턱은 그대로 둔다.** 문턱을 조용히 고치지 않는다는 §7.1 의 약속 그대로다 — 5번 PR 이 같은 봇에게 망 · 무작위를 붙여 정식으로 재고, 선을
못 넘으면 까닭을 적고 멈춘다. README 의 「알고 있는 위험」이 이것을 싣는다. (5번 PR 이 쟀다 — 38.1% 로 못 넘었다 · §7.1.)

### 6.3 대조군 — 반반의 동전

`stages.json` 의 `picker` 는 단계마다 id 하나라 그 한 줄을 `network` 로 바꾸면 대조군이 없다(2026-09-24 §4.4). 그래서 **`StageRoster.Setup`** — 게임과
데모가 판을 세우는 그 한 자리 — 이 2단계의 id 가 `network` 이면 동전을 던진다:

- `Det.RollInt(시도 시드, PickerArm, 100) < picker.network_share_percent` → **망**, 아니면 **무작위**(`uniform` 그대로).
- 갈래는 `StageSetup.Arm`(`network` · `uniform`)이 싣고, 로그와 기록이 그것을 남긴다. 고르기 id 가 `network` 가 아닌 단계는 갈래가 없다(null).
- 망 갈래가 다섯 전부로 선 시도(`thin` · `no_habit`)와 무작위 갈래는 뽑기가 같다 — 그래도 **다른 갈래다.** 분석은 갈래로 가르고 다섯 전부로 선
  까닭은 `reason` 이 싣는다.
- **몫은 70 이다(2026-09-28 · #122).** 반반에서 시작했고, 유저가 무작위 갈래를 30% 로 줄였다 — 플레이하는 사람이 망 보스를 더 자주 만나게.
  공장(무작위 고정)과 평가(갈래를 정해 넘김 · §7.1)는 몫을 안 읽어 학습 데이터와 검증 수치는 그대로다.

  고르기 id · 갈래 · 뽑힌 순서 · 결과 · 틱 · 관측 전부 · (망 갈래면) 좁힌 명부 · 숨통 · 로짓 · 들어 올림 · `reason` · `network.json` 의 sha256.
  줄을 짓고 읽는 것은 순수 `AttemptLog` 이고(왕복 테스트), 파일에 쓰는 것만 Godot 쪽이다.
- **되살리기:** `EXTRA="--history=<파일> --attempt=N" tools/build.sh demo` — 데모가 그 파일에서 **같은 런의 N 앞 기록**으로 고르기를 다시 세운다.
  고르기가 상태 없는 조회라 보스의 순서가 그대로 선다(봇이 싸우므로 판의 길이는 다르다 — 앞머리가 같다). 로그의 `network.json` 해시가 지금과 다르면
  `[W]` — 다른 망이라 다른 명부가 설 수 있다.

### 6.6 로그

| 줄 | 언제 |
|---|---|
| `[net][I] loaded heads=5 features=19 trained_on=<커밋>` | 부팅 |
| `[net][W] stale data_digest=<지금> trained_on=<그때>` | 부팅 · 해시가 다를 때 |
| `[run][I] attempt=N stage=S seed=X picker=network arm=network history=K` | 전투를 세울 때(`arm=` 이 더해진다) |
| `[pick][D] mode=narrowed reason=habit narrowed=… breathing=… logits=… lifts=…` | 망 갈래를 세울 때 |
| `[pick][D] mode=full reason=thin samples=12` · `reason=no_habit` | 다섯 전부로 섰을 때 |
| `[run][D] logged attempt=N path=…` | 디스크에 한 줄을 썼을 때 |

수는 고정 소수(`F3`)로 적는다 — 같은 double 은 같은 글자다.

### 6.7 README

「어떤 망을 어떻게 만드나」를 이 설계에 맞춘다 — 입력은 11축과 근거 수(10 → 11 · 가드), 패턴은 입력이 아니라 **출력의 칸**(태그로는 3연격과 엇박이
같다), 캐릭터는 입력에서 뺐다(1종인 동안 상수), 「그 예측으로 보스를 어떻게 정하나」는 좁힌 명부의 규칙 그대로, 「그래서 지금은 무작위다」는
**반반의 대조군**으로 바뀐다.

## 7. 검증 (5번 PR)

### 7.1 같은 봇에게 망 보스와 무작위 보스

학습에 **안 쓴** 봇 번호 범위(시험 몫 너머)의 함대를 공장의 평가 모드로 돌린다: 같은 봇 · 같은 시도 시드로 2단계를 **망 갈래 고정** 한 번,
**무작위 갈래 고정** 한 번. 짝지은 비교라 봇마다의 차이가 지워진다. 신뢰 구간은 봇을 다시 뽑는 부트스트랩이다.

| 무엇 | 선 |
|---|---|
| **의존 봉인** | §4.6 의 네 줄마다, 그 습관형 봇에게 (가) 그 패턴이 뽑히는 몫이 무작위의 1.5배 이상이고 (나) 2단계 사례의 맞는 비율이 무작위보다 높다 — 구간이 0 을 안 넘는다 |
| **숨통** | 좁힌 시도는 **전부** 숨통 칸을 싣는다(구조상 — 테스트가 못박는다). 숨통 칸의 실제 맞는 비율이 겨냥 칸보다 낮다 |
| **약점 저격이 아니다** | 습관 없이 고르게 약한 봇(반응 0.30 초 이상 · 흔들림 0.08 초 이상 · 혼합형)의 망 갈래 시도 중 80% 이상이 다섯 전부로 선다(`no_habit` · `thin`) |
| **죽음의 나선이 아니다** | 망 보스의 2단계 승률이 무작위의 절반 이상이다 |
| **보정** | 평가 함대의 뽑힌 사례에서 칸마다 ECE ≤ 0.05 |

선을 못 넘으면 문턱(`lift_min` · `max_targeted`)을 조용히 고치지 않는다 — 멈추고 까닭을 적는다.

**5번 PR 이 쟀다 — 다섯 줄 중 둘을 못 넘었다. 멈춘다.** 함대 시드 1 · 봇 100,000 ~ 149,999(학습에 안 쓴 봇) · 2단계에 간 봇 31,580 · 사례는 망 갈래
697,359 · 무작위 갈래 691,335 · 구간은 봇을 다시 뽑는 부트스트랩 1,000번의 95%(`ml/validation.md` 에 전부 있다).

까닭:

- **대시 → 잡기의 몫** — 대시 습관형의 좁힌 시도 중 84% 에서 잡기가, 64% 에서 점프 3연속이 겨냥이다(망은 대시에 기대는 봇에게 점프 ×3 의 착지도
  평균보다 잘 먹힌다고 본다). 겨냥이 둘이면 잡기는 명부의 1/3 이라 몫이 27.5%(무작위 20.0%)에 그친다. 맞는 비율은 올랐다 — 막는 수단이 안 선 것이
  아니라 한 패턴에 덜 몰렸다.
- **약점 저격** — §6.2 의 이른 측정 그대로다(38.9% → 38.1%). 습관 없는 봇도 칸마다의 들어 올림이 0.65 쯤 벌어져 `lift_min` 을 넘는 칸이 흔하다.

**규칙을 바꾸면 — 가늠.** 무작위 갈래의 2단계 시도 111,761 의 입력(규칙과 무관하다)에 규칙의 변형을 돌려, 좁힌 명부 안에서 고르게 뽑힌다고 보고
셈했다. 지금 규칙의 대리값이 실측과 맞는다(고르게 약한 봇 37.4% · 실측 38.1% · 대시 → 잡기 1.36 · 실측 1.38).

## 8. 결정론 — 같은 시드면 같은 결과

- **결정 경로에는 사칙연산과 비교만 둔다.** 표준화 · 순전파(ReLU) · 들어 올림 · 문턱 비교 · 정수 뽑기. 시그모이드(exp) · 로그는 결정에 안 쓴다 —
  기저율의 로짓은 파이썬이 한 번 계산해 데이터로 싣고, 문턱(`lift_min`)은 로짓 공간의 수다. 확률(%)은 사람이 읽는 로그와 보고서에만 나온다.
- IEEE 754 의 + − × ÷ 는 올바르게 반올림된 결과가 하나뿐이라 기기가 달라도 같다. 리플레이 골든이 이미 이것에 기대어 맥과 리눅스에서 같은 판을
  낸다. 순서를 바꾸는 것(SIMD · 병렬 합 · 자동 FMA)을 안 쓴다 — .NET 은 부동소수를 스스로 합치지 않는다.
- 잡음(§3.1)은 균등 난수의 합이다 — `sqrt` · `log` 를 쓰는 정규분포 변환(박스–뮬러)을 안 쓴다.
- 골든(§5.7)이 매 커밋 이것을 확인한다. 어느 기기에서 깨지면 고정소수점 순전파로 간다(대화에서 둘째로 둔 안) — 그때 이 절을 고친다.
- 새 `Det` 도메인 — 번호는 뒤에 더할 뿐이고 있는 번호는 안 바꾼다(CLAUDE.md §4):

| 번호 | 이름 | 쓰는 곳 | PR |
|---|---|---|---|
| 7 | `fleet_bot` | 봇 번호 → 봇의 세션 시드 · 성향 | 1 |
| 8 | `fleet_act` | 봇의 행동 선택 — 수단 · 이번 패턴을 가드로 받나 · 2연격 · 대시 방향 · 리듬 | 1 |
| 9 | `fleet_timing` | 봇의 타이밍 잡음 | 1 |
| 10 | `picker_arm` | 2단계 시도의 동전 — 망 · 무작위 | 4 |

  행동과 잡음을 한 스트림에 안 섞는 이유는 옛 도메인들의 주석과 같다 — 나눠 쓰면 한 판단을 한 번 더 한 것만으로 그 뒤의 모든 다른 판단이 밀린다.
  뽑기는 망도 지금의 `PatternPick`(1)을 쓴다.

| 겨냥 표가 대본의 한 장면이었다 — GIF 의 짝(가드 → 점프 ×3 · 간격 → 돌진)은 순서 · 패턴을 모르는 실수에 기댔다 | 2번 PR 이 원본으로 재서 판정이 막는 수단으로 바꿨다(§4.6). 게임의 수치는 안 고쳤다 — 짝을 되살리려면 패턴을 고치는 설계의 일이다 |
| 축이 패턴을 안 가른다 — "3연격은 패리하고 점프 공격은 넘는다" 는 사람이 "반반" 한 명으로 읽힌다 | 빚으로 둔다(§13). 판정마다의 "고를 수 있었나" 가 의존도의 분모를 이미 가른다 |
| 라벨이 피해의 크기를 안 싣는다 — 칩 하나와 세 대가 같은 1 | 받아들인다. 고르기는 "맞나 안 맞나" 로 충분하다 — 크기는 나중에 머리를 더해 싣는다 |
| 좁힌 명부가 한 패턴을 자주 낸다 — 대시만 쓰는 사람에게 잡기가 절반 | **의도다**(의존 봉인). 답답하면 `max_targeted` · `lift_min` · 비율이 데이터에 있다 |
| 망이 옛 게임을 배운 채 남는다 | `data_digest` 의 `[W]`(§5.6) · 골든이 움직이는 PR 은 다시 학습할지 적는다 |
| 클라우드에서 torch 가 무겁다 — `download.pytorch.org` 가 막혀 PyPI 기본 휠(CUDA 의존 포함, 수 GB)이 온다 | 3번 PR 이 torch 를 걷고 넘파이로 썼다(§5.1) — numpy · pandas 는 수십 MB 다 |
| 어느 기기에서 부동소수가 갈린다 | 골든이 매 커밋 잡는다 — 고정소수점으로 간다(§8) |
| 공장이 너무 느리다 | 2번 PR 이 재서 정한다. 사례는 봇마다 독립이라 코어에 비례한다 |

## 12. 스펙이 정한 것 — 유저가 말하지 않은 자리

| 자리 | 정한 것 | 까닭 |
|---|---|---|
| 함대의 자리 | 새 `FleetBot` · `BotPolicy` 는 그대로 | 스모크 · 데모 · 골든이 `BotPolicy` 위에 서 있다 · `BotChoice` 주석 |
| 성향의 범위 | `tools/factory/fleet.json` | 게임의 수치가 아니라 실험의 조건 — 매니페스트가 해시를 싣는다 |
| 잡음 | 균등 난수 넷의 합 | 사칙연산만(§8) |
| 입력 | 11축 + 개수 8 = 19 · 날것의 개수 · 표준화 | 근거의 크기를 망이 알아야 한다 · 변환 상수를 데이터에 또 두지 않는다 |
| 라벨 | 사례에 `Hit` · `GuardBroken` · `Grabbed` 가 하나라도 있나 · 끝나지 않은 사례는 버린다 | "맞을 확률" 그대로 · 모르는 것을 0 으로 적지 않는다 |
| 사례의 경계 | `CurrentPattern` null → id · 다음 사례 전까지의 그 id 관측 | 관측의 모양(`DodgeEvent`)을 안 바꾼다 |
| 공장의 고르기 | `uniform` 고정 | 다섯 칸이 고르게 덮이고 라벨이 고르기에 안 기운다 |
| 1단계를 못 이긴 봇 | 2단계 표본 없음 · 수만 센다 | 사람도 2단계에 못 간다 — 추론의 모집단과 같게 |
| 나누기 | 봇 번호로 80 · 10 · 10 | 같은 봇이 양쪽에 새면 외운 것을 일반화로 착각한다 |
| 기준선 | 패턴의 기저율 | 사람을 안 보는 예측기를 못 이기면 축에 정보가 없다 |
| 들어 올림 | 로짓 − 기저율의 로짓 | 약점 저격이 아니라 "유독 먹히는" 패턴 — 고르게 약한 사람은 다섯 전부 |
| 동전의 자리 | `StageRoster.Setup` | 게임과 데모가 판을 세우는 한 자리 — 되살리기가 같은 갈래를 얻는다 |
| 동전 | 정수 퍼센트 비교 | 사칙연산 · 사람이 읽는 수 |
| 기록의 단계 | 잘라 쓴 값 | 실제로 싸운 판이다 — #59 3/6 |
| 디스크 | `user://attempts/<세션 시드>.jsonl` 한 줄 한 시도 | 되살리기와 sim-to-real 의 재료 · 자동 업로드 없음 |
| 되살리기 | 데모의 `--history` · `--attempt` | 고르기가 상태 없는 조회라 기록과 시드로 순서가 선다 |
| 오래된 망 | `[W]` | 이상하지만 계속 간다 — 실패로 두면 수치 하나에 공장이 막는다 |
| 파이썬 골든 | 표준 라이브러리 · 같은 연산 순서 | `check` 가 넘파이 없이 돈다 · BLAS 의 순서와 FMA 를 피한다 |

## 13. 하지 않는 것

- **회피 기록 원본을 읽는 모델** — 이 망이 끝나고 사람 데이터로 검증까지 한 뒤 여유가 있으면 따로 한다. 등록표에 구현 하나를 더하면 되므로 지금 정할 것이 없다.
- **실시간 고르기** — 2026-09-24 에 정했다(재시도마다).
- **패턴별 축** — 축을 패턴마다 따로 모으지 않는다. 입력이 두 배가 되고 칸마다 근거가 반이 된다. §11 의 빚이다.
- **캐릭터 입력** — 1종인 동안 상수다.
- **스스로 탈진하는 봇** — 사람은 그럴 수 있지만 겨냥 표의 어느 칸도 그것에 기대지 않는다. sim-to-real 이 짚으면 성향을 더한다.
- **플레이어에게 "보스가 당신을 읽었다" 같은 안내** — 겨냥은 패턴으로만 말한다.
- **1단계의 고르기를 바꾸는 것** — 재는 자리다.
