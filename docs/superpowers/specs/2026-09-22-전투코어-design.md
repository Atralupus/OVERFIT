# 전투 코어 설계

> 2026-09-22 · 첫 하위 프로젝트의 설계 문서.
> 게임 전체 그림과 하위 프로젝트 분해는 1·2절에 두고, 3절부터가 이 스펙의 범위다.

---

## 1. 게임

**보스 하나를 5단계에 걸쳐 잡는 2D 가로 소울라이크.** 단계를 넘을 때마다 보스가 쓰는 패턴이 늘고,
그 패턴은 **이 플레이어가 지금까지 어떻게 피했는지에 따라 고른다.**

플레이어는 시작할 때 캐릭터 셋 중 하나를 고르고, 단계를 깰 때마다 스탯 강화 셋 중 하나를 고른다.

### 확정된 수치

| | |
|---|---|
| 단계 | **5단계** — 보스가 쓰는 패턴 수가 `2 · 3 · 5 · 7 · 10` |
| 회피 수단 | **대시 · 점프 · 패리** 셋 |
| 캐릭터 | 시작 시 3택 — 빠름·짧음 / 중간 / 느림·긺 |
| 강화 | 단계 클리어마다 3택 1. **스탯 증가만** — 공격력 · 공격속도 · 체력 · 스태미나 |
| 보스 | 1종. 단계마다 새로 생성되며 **생성 뒤 패턴은 고정** (재시도해도 안 바뀐다) |
| 보스 크기 | 플레이어 캐릭터의 **4배** |

**9단계가 아니라 5단계인 이유:** 같은 보스를 아홉 번 잡으면 지루하고, 세 번이면 개인화를 관측할 표본이 안 모인다.

### 레퍼런스

**나인 솔즈**(Red Candle Games) 하나다. 2D 가로 · 대시 · 점프 · 패리 중심 · 평평한 보스방 —
우리가 만들려는 것과 구성이 거의 같다.

가져올 것은 셋이다.

- **보스방이 평평하다.** 지형이 조용해야 패턴을 읽는 데 집중된다
- **패턴이 "무엇으로 피하는가"로 또렷이 갈린다.** 점프로 넘는 것 · 대시로 빠지는 것 ·
  패리로 받는 것 · 그냥 거리를 둬야 하는 것. 그 구분이 그대로 7절의 태그가 된다
- **패리가 선택지이지 정답이 아니다.** 패리로 다 되면 다른 축이 죽어서 개인화할 것이 없어진다

### 프로토타입 범위 — 간단하게 간다

이건 **프로토타입이다.** 완성도가 아니라 "루프가 도는가"를 본다.

| | 프로토타입 | 나중 |
|---|---|---|
| 패턴 | **6개** | 30개 |
| 이펙트 | 없음 (히트스톱만) | 잔상 · 섬광 · 스파크 |
| 사운드 | 없음 | |
| UI | 체력바 · 스태미나바 | 나머지 전부 |
| 배경 | 단색 | |

**패턴 6개로 시작하는 이유:** 5단계가 `2·3·5·7·10` 을 쓰지만, 프로토타입에서 보려는 것은
"단계마다 패턴이 늘고 전투가 끝까지 도는가"다. 6개면 1~3단계가 돌고, 그것으로 충분하다.
숫자를 채우는 것은 루프가 도는 것을 본 뒤다.

**"생성 뒤 고정" 이 설계 전체를 떠받친다.** 패턴 선택이 단계 사이에 한 번만 일어나므로
실시간 추론이 없고, 선택 결과를 저장하면 되므로 부동소수점 재현성 문제도 없다.

## 2. 하위 프로젝트 분해와 순서

독립된 subsystem 이 일곱이고, 스펙 하나로 못 쓴다.

| | 무엇 | 전제 |
|---|---|---|
| 1 | **전투 코어** — 대시·패리·공격, 보스 패턴 실행, 히트 판정 | |
| 2 | **패턴 시스템** — 정의 형식, 태그, 등록표 | |
| 3 | **계측** — 회피 이벤트 → 플레이어 축 | |
| 4 | **성장 루프** — 캐릭터 3택 · 강화 3택 · 단계 진행 | 1 |
| 5 | **시뮬레이션 봇 + 데이터 공장** | 1·2·3 |
| 6 | **망 학습 + C# 배포** | 5 |
| 7 | **패턴 선택기** | 6 |

**이 문서는 1·2·3 을 다룬다.** 셋은 서로를 너무 많이 알아서 따로 쓰면 인터페이스가 세 번 바뀐다.

### 딥러닝이 마지막인 이유

봇을 돌릴 전투가 없으면 학습 데이터를 만들 수 없다. 그래서 5·6·7 은 1·2·3 뒤에 온다.

이게 나쁜 소식만은 아니다. **1~4 만으로도 게임이 된다** — 패턴을 무작위로 고르는 소울라이크다.
그리고 그 무작위 선택이 **대조군으로 남는다.** 망이 정말 일하는지 증명할 방법이 그것 말고 없다:
같은 시드·같은 플레이어에게 무작위 보스와 망 보스를 붙여 피격률을 비교한다.

## 3. 에셋과 라이선스

**쓰는 것은 하나다.**

| 에셋 | 라이선스 | 쓸 곳 |
|---|---|---|
| [Duelyst animated sprites (Godot 4)](https://github.com/Jordyfel/duelyst-animated-sprites-godot) — [Open Duelyst](https://github.com/open-duelyst/duelyst) 의 재포장 | **CC0 1.0** | 플레이어 캐릭터 3종 · 보스 |

Counterplay Games 가 2023-01-10 에 소스와 **에셋 전부**를 CC0 로 공개했다("no strings attached").
저작자 표시 의무도 없다. 애드온 저장소의 `duelyst-LICENSE` 가 CC0 1.0 전문이다.

유닛 696종(보스 전용 50종), 애니메이션은 `idle · breathing · run · attack · hit · death`.
이미 Godot 4 SpriteFrames 라 변환 작업이 없다.

### 안 쓰는 것과 그 이유

- **CraftPix 9팩** — 전부 탑다운 4방향이라 가로 시점에 안 맞는다. 그리고 레퍼런스 저장소가
  라이선스 확인을 명시적으로 유보해 둔 상태다("출시 전에는 항목마다 다시 확인해야 한다").
- **Tiny Swords** — 상업적 사용은 가능하나 **재배포 금지** 조건이 있고, 탑다운 지형이다.
- **Kenney (CC0) · OFL 폰트** — 깨끗하다. UI·글꼴이 필요해지는 시점에 추가한다.

### 원본은 커밋하지 않는다

`.import` 만 추적한다. 이유는 재배포 권리가 아니라 **저장소 위생**이다 —
한 번 들어간 바이너리는 히스토리에서 빠지지 않는다. CC0 도 예외가 아니다.
받는 방법은 스크립트(`tools/fetch_duelyst.py`)가 맡고, 출처 기록은 `overfit/assets/LICENSES.md` 하나다.

### 대시·패리 애니메이션이 없다

Duelyst 에 roll/dodge/parry 가 없다. 게임의 핵심 동사 둘에 전용 그림이 없다.

**이펙트로 대신한다.** 2D 액션에서 이 둘의 피드백은 애니메이션이 아니라 이펙트·히트스톱이 결정한다.

| | |
|---|---|
| 대시 | `run` + 잔상 3~4장 + 짧은 모션 블러 |
| 패리 성공 | `hit` 프레임 정지 + 섬광 + 스파크 + 히트스톱 6프레임 |

### 캐릭터 3택이지 무기 3택이 아니다

Duelyst 스프라이트는 **무기가 그림에 박혀 있어** 교체할 레이어가 없다.
단검 스프라이트에 특대검을 들릴 방법이 없으므로, 고르는 것은 캐릭터 자체다.

강화가 스탯 증가뿐인 것이 여기서 이득이다 — **새 아트가 0장 필요하다.**

후보(최종 선택은 눈으로 보고 정한다):

| 성격 | 후보 |
|---|---|
| 빠름 · 짧음 | `neutral_mercdaggerkiri` |
| 중간 | `f1_warblade` · `f6_freeblade` |
| 느림 · 긺 | `f4_underworldbrute` · 골렘 계열 |
| 보스 | `boss_*` 50종 중 1 |

## 4. 층 구조 — 양보하지 않는 것 하나

```
          규칙 층 (순수 C#)
   전투 시뮬레이션 · 패턴 실행 · 히트 판정 · 계측
                  ↑
             InputFrame
          ┌───────┴───────┐
      뷰 (Godot)      시뮬레이션 봇
      키보드 입력       생성된 입력
```

**사람과 봇이 같은 전투 코드를 탄다.** 입력이 `InputFrame` 하나로 규칙 층에 들어가고,
뷰는 키보드를, 봇은 자기 정책을 그 구조체로 바꾼다.

이것이 sim-to-real 간극을 줄이는 **유일한 구조적 장치**다. 봇이 별도 경로를 타면
망은 "봇 전용 전투"를 배우고, 그건 사람에게 아무 의미가 없다.
**나중에 붙일 수 없는 종류의 결정이라 지금 못 박는다.**

그리고 이미 세운 베이스와 같은 방향이다 — 규칙 층이 Godot 을 모르므로 봇을 돌리는 데 창이 필요 없다.
테스트 csproj 의 링크 목록이 그 경계를 컴파일러로 강제한다.

## 5. 입력 계약

```csharp
/// 한 틱의 입력. 뷰와 봇이 같은 것을 만든다.
public readonly record struct InputFrame(
    sbyte Move,    // -1 왼쪽 · 0 · +1 오른쪽
    bool Jump,     // 아래 넷은 전부 **눌린 틱에만** true (엣지)
    bool Dash,
    bool Parry,
    bool Attack);
```

**엣지로 두는 것이 중요하다.** 누르고 있는 상태(레벨)로 두면 봇이 "계속 누르고 있기"로
공짜 성능을 얻고, 그 봇으로 만든 데이터는 사람의 판단을 담지 않는다.
점프 높이 조절처럼 길게 누르는 것이 필요해지면 그때 `JumpHeld` 를 따로 더한다 — 겸하지 않는다.

전투는 **고정 60틱**이다. 리플레이는 화면을 저장하지 않고 **입력 시퀀스와 시드**를 저장한다 —
같은 입력이면 같은 판이므로 그것으로 충분하고, 용량도 작다.

## 6. 공간 — 평평한 바닥 하나

가로는 x, 세로는 점프와 중력이 있다. **지형은 평평한 바닥 하나뿐이고 발판이 없다.**

회피 수단은 셋이다.

| | 무엇을 한다 | 무엇에 걸린다 |
|---|---|---|
| **대시** | 수평으로 빠지며 그 동안 무적 | 타이밍 · 방향 |
| **점프** | 낮은 판정을 넘는다 | 타이밍 · 대공 판정에 취약 |
| **패리** | 제자리에서 막는다 (정확 · 부정확 2단계) | 타이밍 · 패리 불가 패턴 · 연타 징벌 |

점프는 **보스를 넘는 수단이 아니다** — 몸 충돌이 없어 어차피 통과한다(#27). 그 높이는
`height[1]` 이 낮은 판정(`이단 올려베기` 150)은 넘되 높은 판정(`내려찍기 3연` 340 ·
`점프 강타`의 착지 충격 330)은 못 넘는 자리에 선다. 그 경계가 곧 "점프로 피할 수 있는가" 축의 근거다.

**순서는 점프가 먼저다(#28).** #27 에서는 패턴 기하가 이미 서 있어서 정점이 176px 에 갇혔고,
그것이 "화면처럼 높이 뛰는" 요구를 막았다. #28 이 패턴을 통째로 갈아엎으며 순서를 뒤집었다 —
정점을 297~302px 로 정하고 세 패턴의 `height` 를 거기 맞췄다. 한쪽만 고치면 `PatternDataTests` 가 막는다.

### 보스가 4배 크다는 것의 뜻

그림 이야기만이 아니다. **규칙이 따라 바뀐다.**

- 보스 히트박스가 넓어 **근접 거리에서는 거의 항상 닿는다.** 그래서 `distance_bias` 축이
  의미를 가진다 — 붙는 사람과 떨어지는 사람의 피격률이 실제로 갈린다
- 아레나 폭이 보스 폭의 배수로 정해져야 한다. 좁으면 대시로 빠질 곳이 없어
  `dash_direction` 축이 죽는다
- 화면 세로의 상당 부분을 보스가 먹으므로 `anti_air` 패턴이 자연스럽다

캐릭터를 120px 로 잡으면 보스는 480px 다. 1080 세로의 절반에 가깝다.

### 몸은 겹치지 않는다 (구현 뒤 추가) → **걷었다 (이슈 #27)**

처음 구현에는 몸 충돌이 없었다. 보스가 파이터의 **정확한 중심**을 목표로 걸어오고 아무것도 밀어내지 않으니
파이터는 보스 몸(반폭 120) 안에 섰고, 데모 실측 평균 교전거리가 **85px** 였다 — 보스 몸 안이다.
그러면 붙는 사람도 떨어지는 사람도 ≈0 으로 수렴해 `distance_bias` 가 **상수가 된다.**
그래서 밀어내기를 넣었다(#16 · #18). 공중만 통과하도록 한 번 더 좁혔다(#22).

**이슈 #27 에서 그 밀어내기를 통째로 걷었다.** 조작을 나인 솔즈에 맞추는 것이 먼저이고,
그 장르에서 적의 몸은 벽이 아니다 — 지나갈 수 없으면 보스가 붙는 순간 벽 쪽으로 몰려
"읽어도 할 수 있는 것이 없는" 자리가 다시 생긴다. 지금 남은 것은 이것뿐이다:

- 보스는 파이터 중심이 아니라 **자기 쪽으로 `Standoff`(보스 반폭 + 파이터 반폭) 떨어진 자리**를 목표로 선다.
  이건 벽이 아니라 **보스의 걸음**이다 — 파이터는 그 안으로 걸어 들어가고 지나쳐 나간다
- 밀어내기(`Separate` · `PushOutTo` · `SeparatedX`)는 없다. 착지해도 안 밀린다

#### 그 대가 — `distance_bias` 를 무엇이 살리는가

**충돌이 그 축을 살리던 방법은 잃는다.** 그걸 알고 걷었고, 축은 **패턴의 안전 거리대**로 옮겼다.

`점프 강타` 의 착지 충격은 `distance [190, 760]` 이라 **보스에 붙어 있으면 안 맞는** 유일한 판정이다.
그런 패턴이 하나라도 있으면 "붙어야 안전 / 떨어져야 안전" 이 진짜 선택이 되고, 거리는 성향이 아니라
**판단**으로서 축에 남는다. 밀려나서 갈리던 거리는 부산물이었고, 이쪽이 원래 재려던 것이다.

- 겹침이 사라져 붙는 봇의 평균 교전 거리는 다시 0 에 가까워진다. **그건 이제 실패가 아니다** —
  그 자리가 `점프 강타` 앞에서 **정답**이기 때문이다
- 전제: 안쪽 안전지대(`distance[0] > 0`)를 가진 패턴이 **활성 명부에 있어야** 한다.
  `BattleSimTests.점프_강타는_발밑만_살려주고_공중을_벌한다` 와 `PatternDataTests.Dash_direction_이_안을_허용하면_안쪽에_안전지대가_있다`
  가 그 전제를 지킨다
- ✅ **해결(#28).** 전에는 `충격파` 가 `stages.json` 의 4·5단계 명부에만 있어 1~3단계에 거리 판단이
  아예 없었다. 백장의 `점프 강타` 가 그 일을 물려받았고 **1단계 명부부터** 들어 있다

### 발판을 두지 않는 이유

게임성이 아니라 **시뮬레이션 봇** 때문이다.

발판이 생기면 봇이 "지금 어디 설까"를 풀어야 하고, 지형이 조금만 복잡해져도 경로 탐색이 된다.
학습 데이터로 수백만 판을 돌려야 하는데 그 탐색이 매 틱 돌면 데이터 공장이 막힌다.
그 순간 봇 자체가 별도의 AI 프로젝트가 되고, **거기서 딥러닝 단계에 도달하지 못한 채 끝날 수 있다.**

평평한 바닥이면 봇의 정책은 "언제 점프·대시·패리하고 어느 쪽으로 움직이나" 뿐이다 — 사람의 판단과 같은 모양이다.

장르 관습이 여기서 우리 편이다. 나인 솔즈의 보스방도 대부분 평평하다.

## 7. 패턴

패턴 = **타임라인 + 태그**. `overfit/data/patterns.json` 이 진실이다.

```json
"횡베기_2연": {
  "tags": {
    "dash_window": 0.18, "dash_direction": "in",
    "jumpable": false, "anti_air": true,
    "parryable": true, "parry_window": 0.12,
    "punish_greed": true, "reach": "mid",
    "feint": false, "multi_hit": 2, "tracking": false
  },
  "timeline": [
    { "t": 0.00, "kind": "windup", "tell": "raise" },
    { "t": 0.45, "kind": "active", "range": [0.5, 2.2], "damage": 18 },
    { "t": 0.60, "kind": "recover" }
  ]
}
```

회피 수단이 셋이므로 태그도 셋을 각각 다룬다 — `dash_window` 가 0 이면 대시로 못 피하고,
`jumpable` 이 참이면 낮은 판정이라 점프로 넘고, `anti_air` 가 참이면 **공중에 있는 쪽이 더 맞는다**(대공).
이 셋의 조합이 "이 패턴을 무엇으로 피하는가"를 정하고, 그게 곧 의존 봉인의 재료다.

**창은 캐릭터와 패턴 중 좁은 쪽이 이긴다(구현 뒤).** 처음 구현의 `HitResolver` 는 **파이터의 창만** 봤다 —
`대공찌르기` 가 `parry_window: 0.10` 을 중검의 0.12 보다 좁게 선언해도 아무 일도 일어나지 않았고
`dash_window` 도 같았다. 그런데 태그는 망의 입력이라 그 숫자는 **그대로 학습된다.**
거짓말하는 숫자는 없는 숫자보다 나쁘다. 그래서 태그를 지우는 대신 물게 했다 — 유효 창 = min(캐릭터, 패턴).
"빠른 공격은 패리하기 더 어렵다" 는 진짜 설계 레버이고, 좁은 쪽이 이기는 것은 양방향이라
패턴이 넉넉해도 캐릭터의 창이 닫혔으면 맞는다(캐릭터 차이가 안 지워진다).

`dash_window: 0` 은 여전히 **"대시로 못 피한다"** 다. 길이 0 인 창과 값은 같은 자리에 떨어지지만 뜻이 다르고,
`DodgeEvent.DashAvailable` 이 그 뜻(의존도 축의 분모)을 싣는다. 한 틱보다 짧은 양수는 둘 중 어느 쪽도
아니라서 — 값으로는 "가능" 인데 실제로는 한 번도 안에 못 들어간다 — `PatternDataTests` 가 막는다.
같은 이유로 `parryable` 과 `parry_window > 0` 은 같은 말이어야 한다.

태그는 **약 20개**이고, 8절의 플레이어 축과 짝을 이루도록 고른다 —
망의 입력이 (플레이어 잠재 + 무기 + 패턴 태그)이므로 **태그가 성능의 상한을 정한다.**

실행기는 인터페이스 + id→구현 등록표다. 새 패턴이 기존 파일을 안 건드린다.

**안쪽이 안전한 패턴이 적어도 하나 있어야 한다(구현 뒤).** 처음 여섯 패턴은 전부 `distance[0] == 0` 이었다 —
보스에 붙는 것이 안전한 순간이 하나도 없으니 "안으로 파고든다" 가 정답인 상황 자체가 없고,
`dash_direction_bias` 축은 **구조적으로** 상수였다. 죽은 입력은 망의 용량만 먹고 아무것도 가르치지 않는다.
그래서 바깥 고리만 쓸고 지나가는 판정을 넣었다(처음에는 `충격파`, #28 부터는 백장의 `점프 강타`).
안쪽 끝은 몸 충돌이 허용하는 최소 간격보다 넓어야 하고, 점프·패리를 막아 **파고드는 것이 유일한 답**이어야
한다 — 다른 답을 열어 두면 축이 다시 흐려진다.

> 처음부터 30개를 만들지 않는다. **8~10개**로 시작해 루프가 도는 것을 보고 늘린다.
> 100개는 나중에 정할 숫자다 — 최종 단계가 10개만 쓰므로, 태그 축이 잘 퍼져 있으면
> 30~40개로도 개인화 체감은 거의 같다.

## 8. 계측 — 플레이어 축

회피가 일어날 때마다 한 줄을 남긴다.

```
[dodge][I] pattern=횡베기_2연 verb=Dash verdict=Dodged err=-0.083 dir=-1 air=False hp=110
[dodge][I] pattern=지면쓸기 verb=Jump verdict=MissedByHeight err=-0.133 dir=0 air=True hp=110
```

**verb 는 판정 결과에서 끌어낸다.** 그 순간 돌고 있던 행동을 적으면 안 된다 — 점프로 넘긴
낮은 판정이 같이 눌러둔 패리의 공이 되고, 그 패리는 "실패한 패리" 로도 세어져 `parry_rate` 까지
오염된다. 실제로 그랬다. 판정은 안 맞은 이유가 **거리**인지 **높이**인지까지 말한다.

### 패리는 2단계다 (이슈 #27)

| | 창 | 결과 | 관측 |
|---|---|---|---|
| **정확** | 적중 0.133초 전 이내 | 피해 0 · 보스 경직 · 기 +1 · 공중 대시 회복 | `verdict=Parried` |
| **부정확** | 0.133~0.5초 전 | 피해의 50%를 내상 · 지상이면 0.6초 고정 · 기 +1 | `verdict=ParriedLate` |
| 그 밖 | | 그냥 맞는다 | `verdict=Hit` |

**이게 위 문단이 이슈 #16 으로 미뤄 둔 숙제의 답이다.** "늦어서 못 피했다" 와 "아무것도 안 했다" 가
`Verb=None · TimingError=0` 이라는 같은 점이었다 — 패리 행동(0.30초)이 끝나면 시작 시각이 사라졌기 때문이다.
창을 **행동이 아니라 누름**에 붙이고(`Fighter.SinceParryPress`) 중간 단계를 만들자 셋이 세 점으로 갈린다.

- verb 는 정확·부정확 모두 `Parry` 다. 여기서 가르면 `parry_reliance`("다른 수단이 있는데 패리를 골랐나")가
  늦게 누른 패리를 "패리를 안 골랐다" 로 세게 된다 — **고른 것은 같고 결과가 다르다.**
- `parry_rate` 의 분자는 **정확만**이다. 부정확은 절반을 흘리고 굳으므로 성공으로 세면 두 결과가 한 점이 된다.
- 부정확의 수는 축이 아니라 **개수**(`parry_late_n`)로 싣는다 — 10축 계약은 그대로다.
- **연타 징벌:** 앞 누름의 부정확 창 안에서 또 누르면 정확 창이 0.1초로 줄고 그 뒤로는 사라진다.
  받아낸 누름은 사슬을 푼다 — 그래서 "공격이 안 오는데 난사했나" 를 보스에게 묻지 않고도 같은 규칙이 선다.
  이건 감각만이 아니라 **학습 데이터 품질**이다: 매 틱 회피를 고르는 봇이 난사로 공짜 성능을 얻으면
  그 데이터는 사람의 판단을 안 담는다.

verb 는 다섯이다 — `Dash` · `Jump` · `Parry` · `None` · **`Spacing`**. 마지막이 "거리로 빗나갔다" 이고,
그것을 `None`(아무것도 안 하고 서 있었다)과 따로 두는 이유는 둘이 **다른 사실**이기 때문이다:
`Spacing` 은 행동이 아니라 **서 있던 자리**가 피하게 한 것이라 타이밍도 방향도 없다.
한 값으로 합치면 "간격을 잘 잡는 사람" 과 "가만히 있다가 운 좋게 안 닿은 사람" 이 같은 점이 된다.
그렇다고 11번째 축을 만들지는 않는다 — `distance_bias` 가 이미 그 성향을 재고 있고,
`Spacing` 은 그 축이 무엇을 세고 있는지를 관측 줄에서 읽히게 하는 라벨이다.

축은 이 줄들의 **집계**이고, 집계기도 순수 C# 이라 테스트가 Godot 없이 돈다.

| 축 | 무엇 |
|---|---|
| `dash_timing_bias` | 평균 (대시 시작 시각 − 판정 시각). **판정보다 얼마나 먼저 움직였나**라 항상 ≤ 0 이다 |
| `dash_timing_var` | 그 분산. 일관된 실수인가 들쭉날쭉한가 |
| `dash_direction_bias` | 안으로 파고드나 밖으로 도망가나 |
| `jump_timing_bias` | 점프 시점의 평균 편차 |
| `jump_reliance` | 대시·패리로도 피할 수 있는 상황에서 점프를 고른 비율. **분모는 그 "진짜 선택"이 있었던 판정뿐이다** |
| `airborne_at_impact` | 판정이 선 순간 공중이었던 비율. 높으면 `anti_air` 패턴이 아프다 |
| `parry_rate` | 패리 성공률 |
| `parry_reliance` | 다른 수단이 있는데 패리를 고른 비율. 분모는 같은 셈법이다 |
| `greed` | 보스 선딜 중 공격을 시도한 비율 |
| `distance_bias` | 평균 교전 거리 |

10축이다. 회피 수단이 셋이 되면서 7축에서 늘었다.

**두 이름을 고쳐 적었다(구현 뒤).**

- `air_time_ratio` → `airborne_at_impact`. 재는 것이 "공중에 떠 있던 시간의 비율" 이 아니라
  "판정이 선 순간 공중이었나" 의 비율이었다. 전투의 90%를 땅에서 보내도 액티브 프레임마다
  공중이면 1.00 이 나온다. **계산을 안 바꾸고 이름을 바꿨다** — `anti_air` 가 아픈지를 예측하는 데는
  체류 시간보다 피격 순간의 고도가 바로 그 답이라, 재고 있던 쪽이 원래 쓰려던 쪽보다 낫다.
- `*_timing_bias` 의 "음수면 이르다" 를 걷었다. 관측은 판정이 서는 틱에 그 시점 이미 시작돼 있던
  행동만 보므로 값이 **항상 ≤ 0** 이다 — "음수면" 이 아무 정보도 나르지 않았다.
  "늦어서 못 피했다" 를 "아무것도 안 했다" 와 가르는 것은 **판정 뒤까지 기다리는 대신** 부정확 패리가 했다
  (이슈 #27 · 위 표). 늦게 누른 것도 규칙 안에서 무언가를 하므로 관측이 그 자리에서 셋을 가른다.

**두 의존도 축을 조건부로 고쳐 적었다(구현 뒤).** 처음 구현은 `jumps / 전체 관측` — 그냥 사용 비율이었다.
그것은 "점프에 의존한다" 와 **"점프로만 피할 수 있는 패턴만 만났다"** 를 구별하지 못한다. 둘은 봉인할 것이
정반대다 — 전자는 점프를 막아야 하고 후자는 막을 이유가 없다. 그래서 분모를 **그 수단이 가능했고 다른 수단도
가능했던 판정**으로 좁혔다. 근거가 없으면(그런 판정이 하나도 없으면) 다른 축과 같이 `0` 이다.

이게 되려면 관측 줄이 판정의 `dash_window` · `jumpable` · `parryable` 을 들고 다녀야 한다 —
집계기는 이벤트 목록만 받아서 패턴 태그에 손이 안 닿기 때문이다. 방출 시점(`BattleSim.Land`)에 싣는다.

**축 옆에 수단별 관측 수를 같이 싣는다** (`dash_n` · `jump_n` · `parry_n`,
그리고 의존도 축의 분모인 `jump_rel_n` · `parry_rel_n`).
다섯 축은 전체가 아니라 부분집합으로 계산되는데 `samples` 만 붙이면 "관측 10건" 이
"대시 3건으로 낸 분산" 까지 보증하는 것처럼 읽힌다. **축이 아니라 개수라 10축 계약은 그대로다.**

**관측 수를 다시 셌다.** 처음엔 "한 런에 수십 건"으로 잡았는데 짰다 —
소울라이크는 죽는 것이 기본이라, 단계당 5회 시도 × 패턴 10회 노출이면 **단계당 50건, 3단계까지 150건**쯤이다.
죽음이 데이터로는 이득이다. 10축을 추정하기에 모자라지 않다.

**그래도 이보다 늘리지 않는다** — 축을 늘리면 축당 근거가 얇아지고, 그 얇아짐은 조용히 온다.

## 9. 선택 목적 (스펙 7 소관 · 여기 기록만)

**의존 봉인 + 숨통 보장.**

- 많이 쓴 수단을 무효화한다. 패리로 다 막았으면 패리 불가 패턴을, 밖으로만 대시했으면
  안으로 파고들어야 하는 패턴을 준다. **성공했어도 막는다** — 그게 핵심이다.
- 다만 매 단계 **확실히 넘을 수 있는 패턴을 하나 보장한다.** 전부가 낯선 방어전이면
  배울 여유가 없어 그냥 불합리하게 느껴진다. 보장된 하나가 "내가 늘었다"를 확인시킨다.

**약점 저격(실패율 높은 축을 더 요구)은 하지 않는다** — 데스 스파이럴이 되고
초보자일수록 가혹해진다.

## 12. 열린 질문

1. **캐릭터·보스 최종 선택.** 이름으로 후보만 골랐다. 스프라이트를 실제로 띄워 보고 정해야 하므로,
   레퍼런스의 `SpriteGallery` + `shots` 에 해당하는 확인 도구가 먼저 필요할 수 있다.
2. **한 판 길이.** 보스 체력과 플레이어 화력이 정해져야 단계당 관측 수가 나오고,
   그 수가 8절 축의 추정 정확도를 정한다.
3. **스태미나 수치.** 대시·패리·공격의 소모와 회복 속도. 패리 의존도가 의미를 가지려면
   "패리가 대시보다 싸지만 실패가 비싸다" 같은 구조가 필요하다.
4. **회복 수단이 있는가.** 회복은 "언제 위험을 감수하나"를 드러내는 장치라 `greed` 축과 같은 것을 잰다.
   소울라이크라면 있는 편이 자연스럽지만 프로토타입에는 안 넣는다 — 넣으면 축이 하나 더 늘고(`heal_timing`),
   지금 보려는 것("루프가 도는가")에 필요하지 않다.
