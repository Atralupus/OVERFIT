# 전투 코어 설계

> 2026-09-22 · 첫 하위 프로젝트의 설계 문서.
> 게임 전체 그림과 하위 프로젝트 분해는 1·2절에 두고, 3절부터가 이 스펙의 범위다.

---

## 1. 게임

**보스 하나를 5단계에 걸쳐 잡는 2D 가로 소울라이크.** 단계를 넘을 때마다 보스가 쓰는 패턴이 늘고,
그 패턴은 **이 플레이어가 지금까지 어떻게 피했는지에 따라 고른다.**

플레이어는 시작할 때 캐릭터 셋 중 하나를 고르고, 단계를 깰 때마다 스탯 강화 셋 중 하나를 고른다.

### 확정된 수치

| | |
|---|---|
| 단계 | **5단계** — 보스가 쓰는 패턴 수가 `2 · 3 · 5 · 7 · 10` |
| 회피 수단 | **대시 · 패리** 둘 |
| 캐릭터 | 시작 시 3택 — 빠름·짧음 / 중간 / 느림·긺 |
| 강화 | 단계 클리어마다 3택 1. **스탯 증가만** — 공격력 · 공격속도 · 체력 · 스태미나 |
| 보스 | 1종. 단계마다 새로 생성되며 **생성 뒤 패턴은 고정** (재시도해도 안 바뀐다) |

**9단계가 아니라 5단계인 이유:** 같은 보스를 아홉 번 잡으면 지루하고, 세 번이면 개인화를 관측할 표본이 안 모인다.

**"생성 뒤 고정" 이 설계 전체를 떠받친다.** 패턴 선택이 단계 사이에 한 번만 일어나므로
실시간 추론이 없고, 선택 결과를 저장하면 되므로 부동소수점 재현성 문제도 없다.

## 2. 하위 프로젝트 분해와 순서

독립된 subsystem 이 일곱이고, 스펙 하나로 못 쓴다.

| | 무엇 | 전제 |
|---|---|---|
| 1 | **전투 코어** — 대시·패리·공격, 보스 패턴 실행, 히트 판정 | |
| 2 | **패턴 시스템** — 정의 형식, 태그, 등록표 | |
| 3 | **계측** — 회피 이벤트 → 플레이어 축 | |
| 4 | **성장 루프** — 캐릭터 3택 · 강화 3택 · 단계 진행 | 1 |
| 5 | **시뮬레이션 봇 + 데이터 공장** | 1·2·3 |
| 6 | **망 학습 + C# 배포** | 5 |
| 7 | **패턴 선택기** | 6 |

**이 문서는 1·2·3 을 다룬다.** 셋은 서로를 너무 많이 알아서 따로 쓰면 인터페이스가 세 번 바뀐다.

### 딥러닝이 마지막인 이유

봇을 돌릴 전투가 없으면 학습 데이터를 만들 수 없다. 그래서 5·6·7 은 1·2·3 뒤에 온다.

이게 나쁜 소식만은 아니다. **1~4 만으로도 게임이 된다** — 패턴을 무작위로 고르는 소울라이크다.
그리고 그 무작위 선택이 **대조군으로 남는다.** 망이 정말 일하는지 증명할 방법이 그것 말고 없다:
같은 시드·같은 플레이어에게 무작위 보스와 망 보스를 붙여 피격률을 비교한다.

## 3. 에셋과 라이선스

**쓰는 것은 하나다.**

| 에셋 | 라이선스 | 쓸 곳 |
|---|---|---|
| [Duelyst animated sprites (Godot 4)](https://github.com/Jordyfel/duelyst-animated-sprites-godot) — [Open Duelyst](https://github.com/open-duelyst/duelyst) 의 재포장 | **CC0 1.0** | 플레이어 캐릭터 3종 · 보스 |

Counterplay Games 가 2023-01-10 에 소스와 **에셋 전부**를 CC0 로 공개했다("no strings attached").
저작자 표시 의무도 없다. 애드온 저장소의 `duelyst-LICENSE` 가 CC0 1.0 전문이다.

유닛 696종(보스 전용 49종), 애니메이션은 `idle · breathing · walk · attack · hit · dead`.
이미 Godot 4 SpriteFrames 라 변환 작업이 없다.

### 안 쓰는 것과 그 이유

- **CraftPix 9팩** — 전부 탑다운 4방향이라 가로 시점에 안 맞는다. 그리고 레퍼런스 저장소가
  라이선스 확인을 명시적으로 유보해 둔 상태다("출시 전에는 항목마다 다시 확인해야 한다").
- **Tiny Swords** — 상업적 사용은 가능하나 **재배포 금지** 조건이 있고, 탑다운 지형이다.
- **Kenney (CC0) · OFL 폰트** — 깨끗하다. UI·글꼴이 필요해지는 시점에 추가한다.

### 원본은 커밋하지 않는다

`.import` 만 추적한다. 이유는 재배포 권리가 아니라 **저장소 위생**이다 —
한 번 들어간 바이너리는 히스토리에서 빠지지 않는다. CC0 도 예외가 아니다.
받는 방법은 스크립트(`tools/fetch_duelyst.py`)가 맡고, 출처 기록은 `prerelu/assets/LICENSES.md` 하나다.

### 대시·패리 애니메이션이 없다

Duelyst 에 roll/dodge/parry 가 없다. 게임의 핵심 동사 둘에 전용 그림이 없다.

**이펙트로 대신한다.** 2D 액션에서 이 둘의 피드백은 애니메이션이 아니라 이펙트·히트스톱이 결정한다.

| | |
|---|---|
| 대시 | `walk` + 잔상 3~4장 + 짧은 모션 블러 |
| 패리 성공 | `hit` 프레임 정지 + 섬광 + 스파크 + 히트스톱 6프레임 |

### 캐릭터 3택이지 무기 3택이 아니다

Duelyst 스프라이트는 **무기가 그림에 박혀 있어** 교체할 레이어가 없다.
단검 스프라이트에 특대검을 들릴 방법이 없으므로, 고르는 것은 캐릭터 자체다.

강화가 스탯 증가뿐인 것이 여기서 이득이다 — **새 아트가 0장 필요하다.**

후보(최종 선택은 눈으로 보고 정한다):

| 성격 | 후보 |
|---|---|
| 빠름 · 짧음 | `neutral_mercdaggerkiri` |
| 중간 | `f1_warblade` · `f6_freeblade` |
| 느림 · 긺 | `f4_underworldbrute` · 골렘 계열 |
| 보스 | `boss_*` 49종 중 1 |

## 4. 층 구조 — 양보하지 않는 것 하나

```
          규칙 층 (순수 C#)
   전투 시뮬레이션 · 패턴 실행 · 히트 판정 · 계측
                  ↑
             InputFrame
          ┌───────┴───────┐
      뷰 (Godot)      시뮬레이션 봇
      키보드 입력       생성된 입력
```

**사람과 봇이 같은 전투 코드를 탄다.** 입력이 `InputFrame` 하나로 규칙 층에 들어가고,
뷰는 키보드를, 봇은 자기 정책을 그 구조체로 바꾼다.

이것이 sim-to-real 간극을 줄이는 **유일한 구조적 장치**다. 봇이 별도 경로를 타면
망은 "봇 전용 전투"를 배우고, 그건 사람에게 아무 의미가 없다.
**나중에 붙일 수 없는 종류의 결정이라 지금 못 박는다.**

그리고 이미 세운 베이스와 같은 방향이다 — 규칙 층이 Godot 을 모르므로 봇을 돌리는 데 창이 필요 없다.
테스트 csproj 의 링크 목록이 그 경계를 컴파일러로 강제한다.

## 5. 입력 계약

```csharp
/// 한 틱의 입력. 뷰와 봇이 같은 것을 만든다.
public readonly record struct InputFrame(
    sbyte Move,    // -1 왼쪽 · 0 · +1 오른쪽
    bool Dash,     // 눌린 틱에만 true (엣지)
    bool Parry,
    bool Attack);
```

전투는 **고정 60틱**이다. 리플레이는 화면을 저장하지 않고 **입력 시퀀스와 시드**를 저장한다 —
같은 입력이면 같은 판이므로 그것으로 충분하고, 용량도 작다.

## 6. 공간을 1차원으로 둔다

플레이어와 보스의 위치는 **x 하나**다. 그림은 y 를 쓰지만 규칙은 안 쓴다.

> ⚠ **점프를 넣지 않는다는 것은 내가 한 결정이고, 들은 요구가 아니다.**
> 회피 수단을 대시·패리 둘로 정했으므로 점프는 회피에 쓰이지 않는다 —
> 그러면 남는 역할이 이동뿐인데, 좌우 이동과 대시가 이미 그 일을 한다.
> 넣으면 공간이 2차원이 되어 시뮬레이션 비용과 패턴 제작비가 같이 오른다.
> **점프를 원하시면 이 절과 7절의 태그가 통째로 바뀐다** — 지금 말씀해주셔야 한다.

히트박스는 x 구간이다. 회피는 둘뿐이다:

- **대시** — 위치를 옮기면서 그 동안 무적
- **패리** — 위치는 그대로, 활성 창 안에 히트가 들어오면 막는다

**이 단순함이 5절의 데이터 공장을 가능하게 한다.** 수백만 판을 돌려야 하는데
2차원 충돌 판정이 들어가면 비용이 한 자릿수 올라간다. 게임성을 해치지 않으면서
시뮬레이션을 싸게 만드는 자리라 의도적으로 좁게 잡는다.

## 7. 패턴

패턴 = **타임라인 + 태그**. `prerelu/data/patterns.json` 이 진실이다.

```json
"횡베기_2연": {
  "tags": {
    "dash_window": 0.18, "dash_direction": "in", "parryable": true,
    "parry_window": 0.12, "punish_greed": true, "reach": "mid",
    "feint": false, "multi_hit": 2, "tracking": false
  },
  "timeline": [
    { "t": 0.00, "kind": "windup", "tell": "raise" },
    { "t": 0.45, "kind": "active", "range": [0.5, 2.2], "damage": 18 },
    { "t": 0.60, "kind": "recover" }
  ]
}
```

태그는 **약 20개**이고, 6절의 플레이어 축과 짝을 이루도록 고른다 —
망의 입력이 (플레이어 잠재 + 무기 + 패턴 태그)이므로 **태그가 성능의 상한을 정한다.**

실행기는 인터페이스 + id→구현 등록표다. 새 패턴이 기존 파일을 안 건드린다.

> 처음부터 30개를 만들지 않는다. **8~10개**로 시작해 루프가 도는 것을 보고 늘린다.
> 100개는 나중에 정할 숫자다 — 최종 단계가 10개만 쓰므로, 태그 축이 잘 퍼져 있으면
> 30~40개로도 개인화 체감은 거의 같다.

## 8. 계측 — 플레이어 축

회피가 일어날 때마다 한 줄을 남긴다.

```
[dodge][I] pattern=횡베기_2연 verb=dash t_rel=0.12 dir=out result=clean
[dodge][I] pattern=횡베기_2연 verb=parry t_rel=0.31 result=hit
```

축은 이 줄들의 **집계**이고, 집계기도 순수 C# 이라 테스트가 Godot 없이 돈다.

| 축 | 무엇 |
|---|---|
| `dash_timing_bias` | 평균 (대시 시점 − 최적 시점). 음수면 이르다 |
| `dash_timing_var` | 그 분산. 일관된 실수인가 들쭉날쭉한가 |
| `dash_direction_bias` | 안으로 파고드나 밖으로 도망가나 |
| `parry_rate` | 패리 성공률 |
| `parry_reliance` | 대시로도 피할 수 있는 상황에서 패리를 고른 비율 |
| `greed` | 보스 선딜 중 공격을 시도한 비율 |
| `distance_bias` | 평균 교전 거리 |

7축이다. **관측이 한 런에 수십 건뿐이라 이보다 늘리지 않는다** — 축을 늘리면 축당 근거가 얇아진다.

## 9. 선택 목적 (스펙 7 소관 · 여기 기록만)

**의존 봉인 + 숨통 보장.**

- 많이 쓴 수단을 무효화한다. 패리로 다 막았으면 패리 불가 패턴을, 밖으로만 대시했으면
  안으로 파고들어야 하는 패턴을 준다. **성공했어도 막는다** — 그게 핵심이다.
- 다만 매 단계 **확실히 넘을 수 있는 패턴을 하나 보장한다.** 전부가 낯선 방어전이면
  배울 여유가 없어 그냥 불합리하게 느껴진다. 보장된 하나가 "내가 늘었다"를 확인시킨다.

**약점 저격(실패율 높은 축을 더 요구)은 하지 않는다** — 데스 스파이럴이 되고
초보자일수록 가혹해진다.

| | 무엇을 본다 | Godot |

파라미터 봇 함대는 스펙 5 의 몫이다.

리플레이 골든: 고정 시드 + 고정 입력 시퀀스로 한 판을 돌려 결과 해시를 대조한다.
결정론이 깨지면 그 자리에서 빨개진다.

## 11. 이 스펙이 하지 않는 것

망 · 파라미터 봇 함대 · 데이터 공장 · 선택기 · 캐릭터 3택 UI · 강화 3택 UI.
전부 뒤 스펙이다. 이 스펙의 패턴 선택은 **무작위**이고, 그것이 나중의 대조군이 된다.

## 12. 열린 질문

0. **점프 여부.** 6절 참조 — 안 넣기로 했으나 내 판단이다. 뒤집으려면 지금이다.
1. **캐릭터·보스 최종 선택.** 이름으로 후보만 골랐다. 스프라이트를 실제로 띄워 보고 정해야 하므로,
   레퍼런스의 `SpriteGallery` + `shots` 에 해당하는 확인 도구가 먼저 필요할 수 있다.
2. **한 판 길이.** 보스 체력과 플레이어 화력이 정해져야 단계당 관측 수가 나오고,
   그 수가 8절 축의 추정 정확도를 정한다.
3. **스태미나 수치.** 대시·패리·공격의 소모와 회복 속도. 패리 의존도가 의미를 가지려면
   "패리가 대시보다 싸지만 실패가 비싸다" 같은 구조가 필요하다.
